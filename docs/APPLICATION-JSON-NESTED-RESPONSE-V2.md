# Bounded nested application response JSON v2

Status: focused OPT808 source, Project, backend and physical allocation qualification passed.

Audience: agents authoring JSON response composition, compiler contributors,
and reviewers.

`bounded-nested-response.v2` / `JsonCodecProfile::NestedResponseV2` is an
additive encode-only selector. Both canonical bounds remain mandatory:
`--max-string-bytes` 1..64 and `--max-array-items` 1..256. It retains the complete
finite shape, two expanded vectors, depth 8, 64 expanded paths, 1..8 record
fields, 131072-byte output preflight, declaration order, overflow/refusal order,
capability requirements and ordinary owner/runtime limits of
[v1](APPLICATION-JSON-NESTED-RESPONSE-V1.md). V1 derivation and its primitive
String-vector J180 refusal remain independently callable; no original control
is replaced by v2. The request one-vector/264-decoded-String policy is unchanged.

V2 additionally encodes primitive `Vec<string>` using the separately owned
[primitive slot-view contract](PRIMITIVE-STRING-VEC-VIEWS-V1.md). Generated array
helpers receive `values: borrow Vec<string>`, bind `vec_str_at(values, at)` inside
the existing bounded loop, and pass that view to the existing UTF-8 quoted-length
and escape writer. They never extend a temporary/projected slot root, clone a
String/row/vector, construct wrappers, or copy values out for encoding. The
ordinary compiler verifies each actual call, root, loan and generation.

For a root `Root`, the APIs are `json_Root_nested_response_v2_encoded_len` and
`json_Root_nested_response_v2_encode`, returning `RootJsonNestedResponseV2Encode`.
Every generated identity uses `<root-id>.json.nested-response-v2.*`; namespace
selection occurs before inserting opaque authored names and IDs. The current
source, root identity, bounds and exact profile select all generated bytes.
Plan receipts use `bounded-nested-response.v2`; replay recomputes the complete
candidate and rejects forged helper roots, identities, bounds, profile labels
and stale authored revisions. Receipts carry no publication authority.

Complete preflight precedes one exact Bytes reservation. Rendering uses the
existing functional writer and final checked `string_from_utf8` copy directly
inside the Encoded field. This is one buffer reservation and one final String
materialization, not zero-copy or a recoverable native String allocator. Fatal
String/Bytes allocation policy and sticky ordinary Vec allocation refusal remain
unchanged. Neither allocation metrics nor live-owner counts are normalized.

Owning gates are the existing `project::json_codec::nested_response::tests`
module, `project` harness `standard_library::application_json::nested_response::string_vectors`,
and `native` harness `string_settlement::codec_allocation::string_vectors`.
Seven generator checks, 18 Project checks and two native allocation checks
passed. The complete request→decision→response case uses detached owners,
independent JSON values/escaping oracles, empty and duplicate values, NUL/Unicode,
first/last slots, exact/one-over byte and item bounds, two nested paths, exact
131072/131073 escaped wire sizes and one-short output. The output-cap oracle
streams every expected byte without exceeding existing Array/source limits.
Canonical source, current-HIR/graph, repeated generation and exact plan replay
controls remain part of the original owners.

The native probes retain the complete original allocation fault receiver and
observe actual decoded allocations, zero additional allocation or non-slot copy
traffic for slot reads and preflight/short/value refusals, then exactly one buffer
and one String allocation and one final complete payload memcpy. Slot extraction
also performs
real descriptor memcpy; total copy counters retain every such byte, with separate
operation/owner-based counters and an eight-byte payload classification control.
The native probes passed the actual receiving Drop and fatal unpublished-result
controls. The Project cases passed on the interpreter, native C11 O0/O2 and
strict Core Wasm. Matched application measurements remain a separate follow-up.

The versioned suitability-v1 report keeps its closed twelve-profile inventory;
this additive selector is explicitly discoverable in CLI profile help and the
nested-response authoring card. Updating that report requires its own versioned
inventory contract rather than silently changing existing pages.

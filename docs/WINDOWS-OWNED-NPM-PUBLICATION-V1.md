# Windows owned npm publication v1

Status: authored implementation and regressions; unrun and unpromoted.

Audience: compiler contributors, Windows package consumers, and release reviewers.

## Availability and compatibility

Windows Project v8, v9 and v10 npm/Web publication belongs to the unpublished
`semaprax-full` toolchain. `build --target npm`, `--target web`, `--target wasm`
and the default Project build select the same profile-specific six-file package.
The standalone registry `semaprax` CLI and ordinary root library publication
reject these Windows routes with `SPX-W120`, directing the caller to
`semaprax-full`. Rejection precedes output-parent creation. Inline generation,
descriptor replay and read-only agent requests remain available without a host.

This explicitly replaces the earlier pathname-based Windows v8–v10 publisher.
It preserves generated bytes, descriptor/carrier schemas, source admission,
Unix publication, Windows carrier-v1 legacy behavior and carrier-v2–v6 rejection.
Carrier versions v7, v8 and v9 correspond to Project versions v8, v9 and v10;
those version numbers are not interchangeable.

The private Windows route requires an existing output parent. It does not use
the CLI's legacy automatic parent creation or pathname cleanup. Relative output
is resolved once; parent traversal and inadmissible Windows spellings reject.
The final directory leaf uses the existing platform's ASCII child-name rules:
reserved device names, alternate streams, separators and trailing dot/space
spellings reject. Parent directories may have Unicode names. This is an
intentional admission boundary, not a claim of arbitrary Windows path support.

## Semantic ownership

`ProjectSnapshot::build_owned_npm_with` admits only those three exact profiles.
The compiler prepares and independently replays the selected npm carrier from
the retained checked Project, then constructs an opaque `ProjectNpmPublication`.
Its read-only artifact view has no public constructor or capsule-to-plan route.
It contains exactly, in order:

1. `app.wasm`
2. `semaprax.js`
3. `semaprax.bindings.js`
4. `semaprax.bindings.d.ts`
5. `semaprax.api.json`
6. `package.json`

The live snapshot owns the pre-publication source recheck, success latch and
post-publication source recheck. The injected host owns the filesystem effect,
not semantic reconstruction. Host failure retains its primary diagnostic;
success followed by source drift uses the existing publication-uncertainty
diagnostic. A callback error does not prove that no filesystem effect occurred.
The plan and any copied bytes are data, never reusable publication authority.

## Filesystem ownership and settlement

The private toolchain uses only the existing safe interop-platform facade.
Unsafe Windows operations stay in its existing sys quarantine; the registry
crate gains no private dependency and the toolchain gains no unsafe block.

Before staging, the publisher checks the fixed inventory, requested output,
original parent identity, held canonical parent and destination absence. It
prepares an exact inventory and a distinct temporary sibling name. Every file
is created exclusively relative to the authenticated stage handle. Exact bytes
and the complete inventory must agree before publication.

Cleanup authority ends before file-handle settlement and the no-replace rename.
A subsequent settlement, rename or authentication failure leaves residue for
reconciliation; it cannot trigger rollback or regain deletion authority if a
published directory is moved back to its staging name. Before that boundary,
any attempted discard is limited to authenticated, invocation-owned inventory.
Unauthenticated creation failures never authorize adopting or deleting a path.
If directory creation reports a namespace effect without returning authenticated
ownership, the existing fail-stop policy terminates the process rather than
retrying or attempting pathname cleanup.

After rename the publisher reopens and verifies every file through the retained
stage authority, checks the exact six-file inventory, and rechecks destination
and original-parent binding. A successful rename is not sufficient by itself
to report success. Existing foreign destinations are never replaced.

These checks are observations under the existing platform authority contract.
They do not promise permanent pathname binding, isolation from a hostile
same-principal process, crash durability, cross-filesystem publication, or a
general transactional filesystem. Failures may leave an inert stage or a
complete published directory; callers must not infer permission to delete it.

## Required evidence

Promotion requires real v8/v9/v10 six-file byte equality, root and standalone
pre-effect rejection, full-host CLI alias dispatch, source-drift and primary
failure behavior, existing/foreign destination preservation, hostile parent
and stage substitution, partial writes, settlement failure, rename collision,
and post-rename displacement without rollback. Physical Windows evidence must
exercise the existing supported rename paths; Unix and older profiles retain
their preservation gates.

Existing Node product consumers must publish through the real full host on
Windows, not manually materialize inline bytes or skip Windows execution.
`src/project/publication_tests.rs` covers the compiler handoff, callback failure,
source drift and direct-carrier rejection. The private toolchain's
`owned_npm/tests.rs` covers filesystem boundaries, including a real file-length
change rejected by settlement recheck; `owned_npm/tests/project_tests.rs` binds
all three actual Project profiles to their verified inline bytes and descriptors.
The reparse-destination fixture is explicitly ignored until selected on a host
with symbolic-link creation privilege; ignoring it is not passing its gate.
`tests/support/owned_npm_publication.rs` preserves those consumer oracles and
checks standalone aliases before any missing-parent creation. Its existing
offline full-toolchain build helper requires provisioned `SEMAPRAX_LINKER` and
`SEMAPRAX_VCTOOLS` on Windows. The npm publication operation itself launches no
compiler, linker, Node, npm or other process; those prerequisites belong to
building the test's CLI, not to the filesystem publisher.
Authoring these checks is not running them. No local test/build, hosted job,
registry publication or production-support promotion is claimed here.
